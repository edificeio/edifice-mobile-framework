## 1. Ce que fait le module

Module technique, **sans écran ni route propres**. Il fournit :

- l'accès à l'API `/explorer/resources` (dossiers et ressources d'une app ENT, paginés) ;
- aujourd'hui, des fabriques de reducer, d'actions et de sélecteurs, que chaque module consommateur branche dans **son propre** store (actions `<CONSOMMATEUR>_EXPLORER_LOAD_PAGE`) ; après la bascule, **son propre store**, par app (§4) ;
- le template `ResourceExplorer` (grille de dossiers et de ressources, navigation dans les sous-dossiers) et `createResourceExplorerNavBar` (titre de l'en-tête = titre du dossier).

L'utilisateur n'y entre jamais directement : il voit le template dans l'écran d'accueil de `wiki`, `blog`, `homework` et `scrapbook`.

## 4. Dans la bascule

- **Déclaration** (gestes 1, 2) : `module-config.ts` supprimé ; `index.ts` : `export default new CoreModule({ name: 'explorer', scope: ['explorer'], redux: { reducer } })`. `CoreModule` : pas d'app ENT à ouvrir ; l'ancien `hasRight: () => true` (toujours disponible) est le comportement d'un `CoreModule`. `matchEntcoreApp: 'Explorer'` et `storageName` disparaissent.
- **Store d'`explorer`** (décision 6, exception à « reducer et actions ne sont pas ouverts ») : un seul reducer, branché par `redux` dans `index.ts`, state à `state.explorer`, Redux gardé, vidé en fin de session (`createSessionReducer`, qui accepte toute action : CONVENTIONS « Données et état »). Les données sont rangées **par app**, puis par dossier comme aujourd'hui : `{ [app]: { [folderId]: { content?, metadata? } } }`. Chaque action et chaque sélecteur prennent l'app **en plus de leurs paramètres d'avant** : action `loadPage(app, folderId, data, flushPreviousData)` de type `EXPLORER_LOAD_PAGE` ; sélecteur `folder(app, folderId)`. La logique du reducer (fusion paginée `staleOrSplice`, métadonnées des sous-dossiers) ne change pas. Les fabriques (`createExplorerReducer`, `createExplorerActions`, `createExplorerSelectors`, `useExplorerActions`) disparaissent, et avec elles les types de `moduleTool`. Rangement des fichiers : celui de `myapps` (`store/state.ts`, `index.ts`, `action-creators.ts`, `selectors.ts`). Un test du reducer (deux apps, même `folderId`) n'est écrit que si le développeur le demande (`CLAUDE.md`).
- **Clé d'une app** (décision 9) : le nom converti par le service depuis le champ `application` de l'API (`toExplorerApp`, qui lit la table `explorerAppFromEntApplication` du service, décision 13), c'est-à-dire le `name` de l'`EntApp` (`'Wiki'`, `'Blog'`, `'Cahier de texte'`, `'Cahier Multimédia'`, type `ExplorerApp`). **Le template ne convertit rien** (décision 12) : il donne son `context` tel quel au GET (`service.resources.get`) et au sélecteur (`selectExplorerFolder(context, folderId)`), et c'est eux qui convertissent. `resources.get` renvoie la page avec son `app` (`{ app, ...page }`), que le template passe à l'action ; `explorerScreenHeader` lit aussi le store par le sélecteur. Pas de prop `app`. Une application sans app connue : le service lève une erreur avant la requête (rien à ranger dans le store), traitée comme toute erreur de chargement ; le sélecteur ne renvoie rien.
- **Registre** (geste 17) : une ligne dans `src/app/config/modules.ts` (seul fichier touché hors du module). Le scope `explorer` est de nouveau demandé dans le jeton, comme quand l'ancien système chargeait `explorer` en module intégré.
- **Template** (décision 5, revue le 2026-11-25 par la décision 14 : la route est lue par `useRoute`, plus passée en prop) : contenu d'écran réutilisable, qui reçoit la `route` de l'écran consommateur et navigue lui-même. Props : `route` (typée par la nouvelle navigation, params `NavParams | undefined`, sans `NativeStackScreenProps`), `context`, `onOpenResource`, `emptyComponent`. La prop `navigation` disparaît : `useNavigation()` dans le template, pour `push(route.name, { folderId })` ; `useIsFocused` gardé. `moduleConfig` et `selectors` disparaissent : le template lit le store d'`explorer` avec la clé de l'app. Le chargement d'une page (service + dispatch) reste dans le template. Types `NavigationProps`, `ScreenProps`, `NavBarConfig`, `AllProps` réécrits ou retirés ; `NavParams` gardé (params de l'écran consommateur).
- **En-tête** (décision 8) : `explorerScreenHeader(context, homeTitleI18n)` → `({ route }) => ({ title })`, pour `defineScreen({ options })` du consommateur : titre du dossier lu dans le store d'`explorer`, sinon le titre d'accueil ; option `title`, jamais `headerTitle`. `createResourceExplorerNavBar` gardé, `@deprecated`, en façade sur le nouveau store (décision 10).
- **Routes, télémétrie, écrans, modales, `entries`, `withSession`, session, storages, notifications, widgets** : sans objet.
- **Consommateurs** (décision 7) : non touchés ; leurs appels, types et stores ne compilent plus jusqu'à leur bascule (liste en §7). Chemins d'import gardés : `createResourceExplorerNavBar` est réexporté par `templates/resource-explorer/screen.tsx`, `explorerScreenHeader` par `screen.tsx` et `index.ts`.
- **Fait au passage** : `npx eslint --fix` sur le dossier a retiré la ligne vide de `service/index.ts` (les 2 erreurs `prettier` préexistantes, §5, 3). `appName` d'une ressource : `toExplorerApp(item.application) as string`, avec un `ToDo(explorer-migration)` ; avant, la table était lue avec un `any` implicite (même valeur, `undefined` pour une application inconnue), et le type plus précis de `toExplorerApp` créait une erreur TS2322.

## 6. Décisions

1. **Plan du 2026-11-18 écarté** (2026-11-19, développeur) : bascule selon [BASCULE.md](../BASCULE.md) ; la refonte va au backlog (§5), sauf le store (décision 6).
2. **Pas de suffixe de route d'accueil à choisir** (2026-11-19) : le module n'a ni écran ni route.
3. **`~/app/intents` n'arrête pas la bascule** (2026-11-19, décidé seul, à relire) : `explorer` n'en importe qu'une table de noms et des types ; il n'ouvre ni n'enregistre d'intent. Répond à STATUS B5 pour `explorer` : pas bloquant. Depuis la décision 13, `explorer` n'en importe plus que le type `OldEntAppNameOrSynonym`.
4. **`CoreModule`** (2026-11-19, geste 2) : pas d'app ENT à ouvrir ; toujours disponible comme avant (`hasRight: () => true`).
5. **Le template navigue lui-même** (2026-11-23, développeur ; sa `route` est lue par `useRoute` depuis la décision 14 ; remplace la décision du 2026-11-19 « template sans navigation, props d'événement »). Un template est un contenu d'écran réutilisable tel quel, auquel l'écran passe sa `route` : il peut utiliser la navigation directement (`useNavigation()`, `useIsFocused`). Seule la prop `navigation` disparaît. Règle générale : CONVENTIONS « Trois types de composants ».
6. **Un seul store, celui d'`explorer`** (2026-11-23, développeur, repris de l'ancien plan, décision du 2026-11-18) : plus de fabrique ni de slice chez les consommateurs ; `explorer` gère son propre store, en Redux, et y range les données par app. Chaque action (et chaque sélecteur) prend l'app en plus de ses paramètres d'avant. Exception à BASCULE (« reducer, actions… ne sont pas ouverts »). Le reste de la refonte de l'ancien plan reste au backlog (§5, 4 à 7).
7. **Consommateurs cassés en attendant leur bascule** (2026-11-23, développeur) : `blog`, `homework`, `scrapbook`, `wiki` ne sont pas touchés ; les erreurs `tsc` sur leurs appels, types et stores sont acceptées et listées (§4, §7).
8. **En-tête** (2026-11-23, développeur) : nouvelle aide `explorerScreenHeader` pour `defineScreen({ options })` ; `createResourceExplorerNavBar` gardé en `@deprecated` (forme : décision 10).
9. **Clé d'une app** (2026-11-23, développeur) : le nom converti par le service d'`explorer` depuis le champ `application` de l'API, qui doit correspondre au `name` de l'`EntApp`.
10. **`createResourceExplorerNavBar` en façade sur le nouveau store** (2026-11-23, développeur) : `createResourceExplorerNavBar(homeFolderi18n, context)`, `@deprecated`, sur l'ancien `screenOptions` comme avant (en-tête de l'ancienne navigation), titre lu par le nouveau sélecteur. Dans son propre fichier (`templates/resource-explorer/deprecated.ts`), pour isoler la navigation ancienne. Le second argument des anciens navigateurs change (`selectors` → `context`). Conséquence acceptée : `explorer` garde un fichier de navigation ancienne, statut `bascule incomplète` dans [SUIVI.md](SUIVI.md) jusqu'à la suppression de la façade (§5, 12). Option écartée : signature inchangée (`selectors`), qu'aucun consommateur ne pourrait plus remplir.
11. **`model/index.ts` supprimé dans la bascule** (2026-11-23, développeur ; exception à « porter tel quel ») : code mort et cassé depuis `972cccdc3`, importé nulle part ; le nettoyer fait partie de la migration. Retire les 5 erreurs `tsc` du module, sans changement de comportement. `model/types.ts` garde son nom (`wiki` et le template l'importent par ce chemin). Devenue règle générale : BASCULE, geste 21.
12. **La conversion de l'app hors du template** (2026-11-23, développeur) : le template fournit `context.application` tel quel ; il ne passe pas par `toExplorerApp`. La clé du store se calcule dans le service (`resources.get` renvoie `{ app, ...page }`) et dans le sélecteur, qui prend le `context`. Options écartées : indexer le store par `application` brut (revenait sur la décision 9) ; une prop `app` donnée par le consommateur.
13. **Table des noms d'apps dans le service d'`explorer`** (2026-11-23, développeur) : `newEntAppNameFromOldMap` et `NewEntAppName` quittent `src/app/intents.ts` (seul `explorer` les lisait) ; la table devient `explorerAppFromEntApplication` dans `service/index.ts` (nom `application` de l'API → `name` de l'`EntApp`), lue par `toExplorerApp` ; le type `ExplorerApp` est écrit dans le modèle (le modèle n'importe pas le service). Repris de l'ancien plan (décision du 2026-11-17 : « un mapping de noms d'apps ailleurs que dans l'adapter de l'API qui l'impose est un anti-pattern »). L'adapter à part (`service/adapter.ts`) reste au backlog (§5, 4).
14. **Route du template lue par `useRoute`** (2026-11-25, développeur, pendant la préparation de `wiki` : [wiki.md](wiki.md) décisions 2 et 5) : le template n'a plus de prop `route` ; il lit la route de l'écran qui l'affiche par `useRoute()` (ses params donnent le dossier, son nom est repoussé pour ouvrir un sous-dossier). L'écran déclare simplement `StaticScreenProps<ResourceExplorerTemplate.NavParams | undefined>` et ne passe que `context`, `onOpenResource`, `emptyComponent`. `NavParams` devient un `type` (les params d'une route sont un `Record`). Le contournement de `blog` est retiré. Revient sur la décision 5 (« le template reçoit la `route` ») et sur la règle « Template » de [CONVENTIONS.md](../CONVENTIONS.md) pour ce template. Options écartées le même jour : une prop `routeName` typée ; `route` passée en prop avec `name: string` (`ResourceExplorerTemplate.ScreenProps`, le nom typé par les routes rendant circulaires les types des modules) ; un callback `onOpenFolder`.
